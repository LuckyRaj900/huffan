Every message that travels across a network or sits on a disk is made of symbols, and not all symbols are equally common. In ordinary English the letter e appears far more often than the letter z, and the space between words is more common than any letter at all. A fixed-width encoding ignores this fact. It spends the same number of bits on a frequent letter as on a rare one, and that is wasteful.

The idea behind variable-length coding is simple: give short codes to common symbols and long codes to rare ones. If the code lengths are chosen well, the average number of bits per symbol drops, and the whole message shrinks without losing a single character. The difficulty lies in the word well. Codes of different lengths can be confusing, because the decoder must know where one code ends and the next begins. The cure is to insist on a prefix-free code, in which no code word is the beginning of another. With such a code the decoder never has to guess or look ahead; it simply reads bits until it has matched a complete code word, writes down the symbol, and starts fresh.

In 1952 a graduate student named David Huffman found a way to build the best possible prefix-free code for a given set of symbol frequencies. His method is a classic example of a greedy algorithm. Begin by treating every symbol as a tiny tree with a single leaf, labelled with its frequency. Then repeat one step until only one tree remains: take the two trees with the smallest total frequency, join them under a new parent node whose frequency is the sum of the two, and put the new tree back into the pool. Rare symbols are merged first, so they end up deep in the final tree, far from the root. Common symbols are merged late, so they stay close to the root and receive short codes.

Reading the code for a symbol is just a walk from the root to its leaf. Every time the walk turns left, write a zero; every time it turns right, write a one. Because symbols live only at the leaves, no path can be the beginning of another path, and the prefix-free property comes for free. Decoding uses the same tree in reverse. The decoder starts at the root, follows one edge for each bit it reads, and whenever it arrives at a leaf it outputs that leaf's symbol and jumps back to the root.

Why is the greedy choice safe? The argument has two parts. First, in some optimal tree the two least frequent symbols are siblings at the deepest level, because swapping a rare symbol with a deeper, more frequent one can only make the total cost smaller or equal. Second, once those two symbols are merged into a single super-symbol, what remains is a smaller instance of exactly the same problem. An optimal solution to the smaller problem, expanded back out, gives an optimal solution to the original one. Greedy choice plus optimal substructure is the standard recipe for a correct greedy algorithm.

The running time is easy to state. Counting frequencies takes one pass over the text. If there are k distinct symbols, building the tree takes k minus one merges, and each merge costs a logarithmic amount of work in a binary heap, so the tree costs O(k log k). Encoding and decoding each take time proportional to the number of characters, since every bit is handled once. For text with a small alphabet, k is tiny and the whole process is essentially linear.

How much can we expect to save? Information theory gives a floor. The entropy of the source, measured in bits per symbol, is the best average any lossless symbol-by-symbol code can reach, and Huffman coding always lands within one bit of it. For English prose the entropy of single letters is a little over four bits, so a text stored at eight bits per character can shrink by roughly forty-five percent. Source code behaves similarly, though its heavy use of spaces, brackets and short keywords changes the balance. Text produced by a random number generator is the hard case. When every character is equally likely there is nothing to exploit, and the saving depends only on how far the alphabet size is from a power of two.

Practical compressors go further. They look for repeated phrases, model the context in which a symbol appears, and combine several techniques in a pipeline. Yet many of them still finish with a Huffman stage, because a well-built prefix code is fast, simple, and hard to beat once the data has been prepared. That is why an idea from 1952 is still running on your phone today.
